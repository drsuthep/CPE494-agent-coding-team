# AGENTS.md

This file gives Codex and other AI coding assistants the operating rules for the CPE494 Agent Coding Lab.

## Project Summary

This project is a teaching lab for **CPE494**. The goal is to demonstrate how AI agents can work together as a software engineering team to build an enterprise-style application from scratch.

The demo application is an **ERP Invoice application**. Students will study this demo, then adapt the same approach to build a different application such as a Student Registration app.

The project intentionally starts with **pure Python orchestration** instead of ADK or MCP so students can clearly understand the agent workflow. Later, students may convert the workflow to use **Google ADK** and **MCP tools**.

## Prompt and Specification Separation

Keep prompts and specifications separate.

```text

```

Do not move project requirements into role prompts unless they are truly about agent behavior.

## Main Agent Roles

### Architect Agent

The Architect analyzes requirements and produces:

- human-readable technical manifest
- file plan
- task list
- JSON task list for the orchestrator

The Architect does **not** write code.

Architect must enforce:

- English-only UI
- database primary key named exactly `id`
- every table/entity includes `rowversion`
- header + line item saves use atomic transactions
- logic/database naming should use `snake_case`
- UI must follow Zen Green theme
- output must end with a machine-readable JSON task list

### Coder Agent

The Coder generates raw source code.

The Coder must output only source code. Do not include Markdown fences or explanations.

The Coder must follow:

- English-only UI
- `snake_case` naming for C# logic and database properties where required
- `id` primary key
- `rowversion`
- transactional save logic where needed
- Zen Green theme
- right-aligned numeric and currency fields
- English tooltips on buttons
- red asterisks for required fields
- appropriate validation display

For UI-related files such as `.cshtml`, `.css`, layout files, and form/list pages, the Coder should receive a compact UI checklist from `ui_specs/erp_invoice_ui.md`.

### Logic Tester Agent

The Logic Tester audits generated code for:

- database integrity
- `id` primary key
- `rowversion`
- `snake_case` naming
- transaction safety
- syntax issues
- dependency injection
- parameterized queries or EF Core usage
- input validation
- English-only code/messages

The Logic Tester must respond with `PASS` if the file passes. Otherwise, it must return a concise list of issues.

### UI Auditor Agent

The UI Auditor checks:

- English-only UI
- Zen Green theme
- dark green headers/title strips, preferably `#004d40`, with white text
- light green/mint accents
- rounded borders
- Tabulator grid styling where grids are used
- right-aligned numeric/currency fields
- English tooltips for all action buttons
- Font Awesome icons where appropriate
- red asterisks for required fields
- header-field validation as red text below fields
- line-item/grid validation as floating tooltip-style messages
- responsive attribute-value header layouts
- horizontal scrolling for grids on small screens

The UI Auditor must respond with `PASS` if the file passes. Otherwise, it must return a concise list of discrepancies.

## Runtime Logging and Traceability

Every notebook run must create a unique run folder.

```text
outputs/runs/<run_id>/
```

Each run folder should contain:

```text
run_manifest.json
input_snapshot/
input_snapshot_manifest.json
gemini_calls.jsonl
architect_manifest.md
tasks.json
attempts/
generated_files/
audit_logs.jsonl
workflow_result.json
applied_files.json
command_logs.jsonl
```

### run_manifest.json

Stores:

- run ID
- phase ID
- phase goal
- timestamp
- agent repo Git commit hash
- target app repo Git commit hash
- Git status information
- input file hashes

### input_snapshot/

Copies of all prompts and specs used in the run.

This is important because prompts/specs may change later. The snapshot shows exactly what Gemini saw during that run.

### gemini_calls.jsonl

Logs every Gemini call.

Each line should contain:

- run ID
- timestamp
- agent name
- model name
- metadata
- full prompt text
- full response text
- status

This is the main traceability artifact.

### attempts/

Stores every generated attempt, even failed ones.

### generated_files/

Stores only files that passed both Logic Tester and UI Auditor.

### audit_logs.jsonl

Stores audit results per file and per attempt.

### applied_files.json

Records which generated files were applied to the target app repo.

### command_logs.jsonl

Records command outputs such as:

- `dotnet build`
- `git status`
- `git diff`

## Versioning Strategy

Do not create filenames like:

```text
erp_invoice_logic_v1.md
erp_invoice_logic_v2.md
final_final.md
```

Use stable filenames and Git commits.

Correct approach:

```text
stable filename + Git commit + run snapshot
```

When prompts or specs are refined:

```bash
git add prompts/ logic_specs/ ui_specs/
git commit -m "Refine current phase UI validation rules"
```

Then rerun the notebook. The run folder will capture:

- new Git commit hash
- snapshot of updated files
- new Gemini calls and responses

## Agent Output Safety

The notebook must not immediately overwrite the target app repo.

Recommended flow:

```text
generate -> audit -> save to generated_files -> human approve -> apply to app repo
```

## Feature Bundles

Some files should be treated as a bundle.

Example:

```text
Pages/Login.cshtml
Pages/Login.cshtml.cs
```

Even if one passes and the other fails, do not apply only half of the feature.

Future improvement: add `feature_group` and `depends_on` fields to the task JSON so the orchestrator can apply only complete feature groups.

Example:

```json
{
  "file_name": "Pages/Login.cshtml",
  "feature_group": "login_placeholder",
  "depends_on": ["Pages/Login.cshtml.cs"],
  "task_description": "Create the English-only Zen Green Login page."
}
```

Better grouped structure:

```json
{
  "feature_group": "login_placeholder",
  "files": [
    "Pages/Login.cshtml",
    "Pages/Login.cshtml.cs"
  ]
}
```

Rule:

```text
Only apply a feature group if all files in the group pass.
```

## Retry Strategy

Use:

```text
MAX_ATTEMPTS = 3
```

Retries should not be identical.

Use this pattern:

```text
Attempt 1: normal generation
Attempt 2: retry with audit feedback
Attempt 3: retry with audit feedback + stricter checklist + explicit final warning
```

More than 3 attempts usually means the task, specs, or prompt is unclear.

## Authorization Scope Decision

Authentication and authorization infrastructure are out of scope for this teaching version.

- Assume the user is authenticated before entering this app.
- Do not implement login, set password, change password, password reset, or role-based menu permissions unless explicitly requested in a future sprint.
- Once inside the app, the user may access all menus and pages.
