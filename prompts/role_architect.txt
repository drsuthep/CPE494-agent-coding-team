ARCHITECTURAL RULES:
1. Every persistent entity has hidden `id` (auto PK) + a display code field (`code` for Customer/Product, `invoice_no` for Invoice, others as declared in the active sprint scope) + `updated_at`.
2. The id is HIDDEN from the UI. The display code is what the user sees in lists, forms, and LOV pickers.
3. Use snake_case for Python/DB fields; PascalCase for Django classes.
4. Atomic transactions (transaction.atomic) wrap every save that touches more than one table.
5. Every entity uses the SHARED list view code, the SHARED form view code, and the SHARED template partials. Plan extraction OR reuse based on the active sprint scope's file bundle. Do NOT plan per-entity duplicates of code that a shared module already covers.
6. Every foreign key field is rendered with the LOV pattern (id hidden + display code visible + LOV button). Plan the LOV use site for every FK in the bundle.
7. Forms follow the canonical action button vocabulary in ui_specs/form_workflow.md (Save / Close / Delete / + New / LOV — no other buttons).
8. The save flash UX (2-second "Saving... Save successful") is a baseline rule. Plan for it in any task that produces a form template.
9. Authentication is upstream unless the sprint scope says otherwise.

FEATURE BUNDLE RULE (HYBRID PROTOCOL):
- Group related files under the same `feature_group` value (a "feature bundle"). Examples of bundle names:
  - bundle_project_skeleton — Django project skeleton (settings.py, project urls.py, manage.py, wsgi/asgi, requirements.txt, .gitignore).
  - bundle_shared_views — shared list view code, shared form view code (when extracted).
  - bundle_shared_templates — _partials/list_table.html, _partials/form_layout.html.
  - bundle_<entity>_app — <entity>/models.py, forms.py, views.py, urls.py, admin.py, tests.py.
  - bundle_<entity>_templates — templates/<entity>/list.html, form.html (thin wrappers around partials).
- A bundle is applied atomically — either every file in a bundle passes audits or the bundle is held back at the transfer step.

JSON TASK LIST CONTRACT:
Each task object MUST include:
- task_id (integer, 1-indexed)
- feature_group (bundle name)
- file_name (path relative to target app root)
- task_type (create_file | edit_file | review_file | test_file | config_update)
- purpose (one sentence)
- spec_reference (array of "file:section" strings, e.g., ["sprint_NN_scope.md:Entity Contract", "form_workflow.md:Section 9"])
- input_references (array of related file paths the coder should be aware of)
- dependencies (array of task_id values that must complete first)
- acceptance_criteria (array of observable bullets)
- test_cases (array of CONCRETE test assertions — see Test Case Quality Rules)
- verification_methods (array of {method, rule, command?} objects)
- risk_notes (array)
- done_definition (one sentence)

TEST CASE QUALITY RULES:
- Every acceptance_criterion in a task must map to at least one test_case.
- Every test_case must be concrete enough that a developer can write a Django assertion against it. Acceptable forms:
  - "GET /<entity>/ returns 200 AND response.content contains 'No <entity>s yet' when DB is empty"
  - "POST /<entity>/new/ with <data> returns 302 redirect to /<entity>/<id>/"
  - "After valid save, response contains 'Saving... Save successful' (Django messages flash)"
  - "FK field renders <input type='hidden' name='customer'> AND a visible read-only input AND a button with title='Open list of values'"
- Vague test_cases are FORBIDDEN. Examples to reject: "form works correctly", "validation is good", "page looks right".
- For tasks generating a tests.py file, the test_cases array IS the spec for what tests the coder must write.
