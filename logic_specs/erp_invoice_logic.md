# ERP Invoice App Logic Specifications

## 1. Purpose

This document defines the non-UI logic, architecture, data, and coding rules for the ERP Invoice application generated by the multi-agent coding team.

The target application is an English-only ASP.NET Core Razor Pages ERP module. The visual style is defined separately in `ui_specs/erp_invoice_ui.md`.

## 2. Target Technology Stack

- ASP.NET Core Razor Pages
- C#
- Entity Framework Core
- SQL Server LocalDB (`(localdb)\\MSSQLLocalDB`)
- Git for version control
- Tabulator (local static files in app repo) and Font Awesome may be used by UI code where appropriate

## 3. Strict Language Rule

All generated source code, UI labels, validation messages, comments, menu text, button text, tooltips, and hardcoded strings must be English only.

Thai text may appear in the visual reference PDF, but it must be treated only as visual guidance. Any Thai label must be translated into English before implementation.

## 4. Naming Standards

Use `snake_case` for:

- C# entity properties
- C# variables where practical
- database field names
- JSON property names used by the app
- form field names where possible

Use `ALL_CAPS_WITH_UNDERSCORES` for constants.

Use clear English names for classes, pages, handlers, services, and folders.

## 5. Database Standards

Every database entity must include:

- `id`: integer primary key, auto-increment
- `rowversion`: byte array used for optimistic concurrency

Every table must have a clear purpose and must avoid mixing unrelated responsibilities.

Foreign keys must be named using snake_case and must clearly identify the referenced entity, for example:

- `customer_id`
- `product_id`
- `invoice_id`

## 7. Transaction Rules

All save operations involving invoice headers and invoice lines must be atomic.

A complete invoice save must either:

- save the invoice header and all line items successfully, or
- roll back the entire operation

Use EF Core transaction support such as `Database.BeginTransactionAsync()` when saving header and line data together.

## 8. Validation Rules

Validation must be performed on the server even if client-side validation exists.

Required validation categories:

- required field validation
- numeric range validation
- unique code validation
- valid foreign key validation
- optimistic concurrency validation
- invoice total recalculation

The UI style for displaying validation messages is defined in `ui_specs/erp_invoice_ui.md`.

## 9. Security Rules

- Assume users are authenticated by an upstream system before entering this application.
- Do not implement login, password setup, password change, password reset, or role-based access checks in this scope.
- Use Entity Framework Core or parameterized queries to prevent SQL injection.
- Validate user input before saving.
- In this teaching version, any user who enters the app can access all menus and pages.

## 10. Code Quality Rules

Generated code must:

- compile without syntax errors
- use dependency injection for data context and services
- avoid duplicated business logic where practical
- keep page model code readable
- separate reusable services when logic becomes complex
- avoid hardcoding business data in UI files

## 12. Auditor Checklist for Logic Tester

The Logic Tester must reject code if it violates any of these rules:

- non-English strings appear in generated code
- missing `id` primary key on an entity
- missing `rowversion` on an entity
- inconsistent snake_case naming for properties or fields
- invoice header and line save is not transaction-safe
- totals are accepted from browser without server recalculation
- SQL injection risk exists
- missing server-side validation for important input
- obvious syntax or namespace errors exist
- dependency injection is missing or misused
